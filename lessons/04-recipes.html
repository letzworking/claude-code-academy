1. 레거시 모듈 흐름 파악

상황: 처음 맡은 정산 모듈. Controller부터 DB까지 어떻게 흘러가는지 모른다.

프롬프트
/settlement/monthly API 요청이 들어왔을 때의 처리 흐름을
Controller → Service → Mapper → 테이블 순서로 추적해줘.
각 단계마다 클래스명, 메서드명, 핵심 로직 한 줄 설명을 붙여줘.
트랜잭션 경계와 외부 시스템 호출이 있으면 따로 표시해줘.
기대 결과
호출 순서대로 정리된 목록, 트랜잭션 범위, 외부 API·배치 연계 지점
주의점
AOP·인터셉터·이벤트 리스너처럼 코드 흐름에 드러나지 않는 부분은 놓칠 수 있습니다. "AOP나 이벤트로 끼어드는 처리도 찾아줘"라고 한 번 더 물어보세요.
🗄️

2. MyBatis 동적 쿼리 해석·튜닝

상황: <if>, <choose>, <foreach>가 뒤엉킨 XML. 실제로 어떤 SQL이 나가는지 감이 안 온다.

프롬프트
OrderMapper.xml의 selectOrderList 쿼리를 분석해줘.
1) 파라미터 조합별로 실제 생성되는 SQL을 2~3가지 예시로 보여줘
2) 인덱스를 못 탈 것 같은 조건이나 풀스캔 위험을 짚어줘
3) 개선안이 있으면 제안만 하고, XML은 아직 수정하지 마
기대 결과
조건별 완성 SQL, 성능 위험 지점(함수 감싼 컬럼, LIKE 앞 와일드카드, OR 남용 등), 개선 제안
주의점
Claude는 실제 DB의 인덱스·데이터 분포를 모릅니다. 튜닝 제안은 반드시 실행 계획(EXPLAIN)으로 검증하세요. 인덱스 DDL 파일이 있다면 함께 알려주면 정확도가 올라갑니다.
🧪

3. JUnit 테스트 만들기

상황: 테스트가 하나도 없는 핵심 서비스. 손대기 전에 안전망이 필요하다.

프롬프트
CouponService에 대한 단위 테스트를 작성해줘.
- JUnit 5 + Mockito, 기존 테스트 코드 스타일을 먼저 참고해
- 정상 케이스, 경계값, 예외 케이스를 각각 포함
- 테스트명은 한국어 @DisplayName으로
- 작성 후 ./gradlew test --tests "*CouponServiceTest" 로 실행해서 통과시켜줘
기대 결과
실행 가능한 테스트 클래스와, 실제 실행 결과(통과/실패)까지
주의점
테스트가 "현재 동작"을 그대로 박제할 수 있습니다. 현재 동작 자체가 버그라면 테스트도 틀린 것이 됩니다. 테스트 이름과 기대값을 읽어보고 비즈니스 규칙과 맞는지 꼭 확인하세요. Maven이면 명령을 mvn test로 바꾸면 됩니다.
🐞

4. 버그 재현 → 수정

상황: 운영에서 NullPointerException이 간헐적으로 발생한다. 스택트레이스는 있다.

프롬프트
아래 에러가 운영에서 간헐적으로 발생해.
원인을 분석하고, 먼저 이 에러를 재현하는 실패 테스트를 만든 다음,
최소한의 수정으로 테스트를 통과시켜줘. 관련 없는 코드는 건드리지 마.

(여기에 스택트레이스 붙여넣기)
기대 결과
원인 설명 → 실패하는 테스트 → 수정 → 테스트 통과 순서의 작업
주의점
"간헐적"인 버그는 데이터나 타이밍에 따라 다르므로 언제 주로 발생하는지 정보를 함께 주세요. 로그에 고객 정보 등 민감 데이터가 있다면 지우고 붙여넣으세요.
🔧

5. 안전한 리팩터링

상황: 800줄짜리 서비스 메서드. 고치고 싶지만 무서워서 못 건드렸다.

프롬프트 — Plan 모드에서 시작 (Shift+Tab)
OrderService.processOrder() 메서드를 리팩터링하고 싶어.
1) 먼저 현재 동작을 보호할 테스트가 충분한지 확인해줘
2) 메서드를 어떤 단위로 나눌지 계획을 세워서 보여줘
3) 내가 계획을 승인하면 한 단계씩 진행하고, 단계마다 테스트를 돌려줘
외부에 공개된 메서드 시그니처는 바꾸지 마.
기대 결과
테스트 보강 → 분리 계획 → 승인 → 단계별 변경과 테스트 결과
주의점
한 번에 크게 바꾸면 리뷰가 불가능합니다. "단계마다 멈춰서 보여줘"라고 해서 리뷰할 수 있는 크기로 받으세요. 단계마다 커밋해 두면 되돌리기도 쉽습니다.
📝

6. 커밋 메시지 · PR 설명

상황: 작업은 끝났는데 PR 설명 쓰기가 귀찮다.

프롬프트
지금 브랜치의 변경 내용(main 대비)을 보고 PR 설명을 써줘.
형식: ## 배경 / ## 변경 내용 / ## 테스트 방법 / ## 리뷰 포인트
리뷰어가 특히 봐야 할 위험한 변경이 있으면 리뷰 포인트에 강조해줘.
기대 결과
diff를 근거로 한 구조화된 PR 설명 초안
주의점
"왜 이 변경을 했는지"는 코드에 없으니 Claude가 추측합니다. 배경 부분은 직접 다듬으세요. 커밋 전 스스로 점검하고 싶다면 /review로 변경 내용 리뷰를 받아볼 수도 있습니다.

검증 방법 포함"테스트 실행해서 통과시켜줘"AI가 스스로 결과를 확인
